# Internationalization (i18n) architecture

Status: **Phase 2.1 — infrastructure only.** English is the only live locale.
Spanish (`es`), French (`fr`), Japanese (`ja`) and Korean (`ko`) are configured
as `planned` and are not routed: every `/es/...`, `/fr/...`, `/ja/...`,
`/ko/...` and `/en/...` URL returns 404.

## Stack

- **next-intl 4** (pinned exactly) for message loading and formatting in Server
  and Client Components.
- **No middleware.** There is no locale detection, no locale cookie and no
  redirect. Routing is resolved by the file system only, so every page stays
  statically pre-rendered and query strings (UTM etc.) are never touched.

## URL rules

| Locale | Homepage | Example page |
|---|---|---|
| en (default) | `/` | `/support` |
| es | `/es` | `/es/support` |
| fr | `/fr` | `/fr/support` |
| ja | `/ja` | `/ja/support` |
| ko (later) | `/ko` | `/ko/support` |

- English never has a prefix and there is no `/en/...` URL.
- Paths have no trailing slash (Next.js default, unchanged from production).

## File layout

```
i18n/config.ts          Locale list, status (live | planned), path helpers. No framework imports.
i18n/routing.ts         next-intl routing definition (as-needed prefix, detection/cookie off).
i18n/request.ts         Loads messages/<locale>.json for Server Components.
messages/en.json        English messages (empty until copy is extracted).
components/root-document.tsx   Shared <html lang>/<body>, NextIntlClientProvider, Analytics.

app/(en)/               English, root layout with <html lang="en">. "(en)" is not in the URL.
  layout.tsx, page.tsx, support/, ...privacy pages, account-deletion/, instagram/, tiktok/
app/[locale]/           Root layout for prefixed locales. Only "live" locales are generated
  layout.tsx            (dynamicParams = false), everything else is a 404.
app/global-not-found.tsx  Site-wide 404 (needed because there is no top-level layout).
app/sitemap.ts, app/robots.ts, app/opengraph-image.tsx, app/twitter-image.tsx
lib/site.ts             INDEXABLE_PAGES registry (path, locales, localizedPaths).
lib/metadata.ts         pageMetadata() with canonical + hreflang; shared root metadata.
```

Two root layouts are used (Next.js "multiple root layouts") so each locale gets
a correct server-rendered `<html lang>` without middleware. Navigating between
`(en)` and `[locale]` pages triggers a full page load, which is expected for a
language change.

## How a page becomes available in a language

A localized page is only routed, listed in the sitemap and advertised via
hreflang when **all** of these are true:

1. The locale's `status` is `"live"` in `i18n/config.ts`.
2. A route file exists under `app/[locale]/...`.
3. The page's `INDEXABLE_PAGES` entry in `lib/site.ts` lists the locale in
   `locales` (defaults to English only).

So untranslated placeholders can't be indexed: a missing route is a 404, and
a page without a translation is never advertised.

## Launch checklist for a new locale (e.g. Spanish)

1. Create `messages/es.json` with the same keys as `messages/en.json`, translated.
2. Add the localized route files under `app/[locale]/` (e.g. `page.tsx`,
   `support/page.tsx`). Each page:
   - calls `setRequestLocale(locale)` (keeps static rendering),
   - exports `generateMetadata` using `pageMetadata({ locale, path, availableLocales, ... })`
     with translated title/description.
3. Add `opengraph-image.tsx` / `twitter-image.tsx` under `app/[locale]/` with
   translated text (they are served at `/es/opengraph-image`, which
   `pageMetadata` already references for that locale).
4. Add `"es"` to `locales` on each translated page in `lib/site.ts`.
5. Set `status: "live"` for `es` in `i18n/config.ts`.
6. Build and check: `/es/...` returns 200 with `<html lang="es">`, a
   self-referencing canonical, reciprocal hreflang (`en`, `es`, `x-default`)
   on both language versions, and sitemap `xhtml:link` alternates.

## Managing translations

- `messages/<locale>.json`, one file per locale, namespaced by page or
  component (`"Home": {...}`, `"Support": {...}`, `"Faq": {...}`).
- English is the source of truth. Keys are added to `en.json` first, then
  translated. A key missing from a translation should block that locale's
  launch rather than fall back silently.
- Marketing copy is translated by humans or reviewed by a native speaker. Do
  not publish raw machine translation for product or legal claims.
- Legal pages (privacy policies, account deletion) stay English-only unless
  the business decides to translate them; they are not listed in other
  locales' sitemaps or hreflang until then.
- **Before translating the homepage**, `components/landing-page.tsx` (a single
  client component) should be split into server-rendered sections with small
  client islands. Copy can then come from `getTranslations()` on the server and
  stays in the initial HTML, including the FAQ answers.

## Multilingual blog (Phase 3)

- Routes: `app/(en)/blog/[slug]/page.tsx` for English and
  `app/[locale]/blog/[slug]/page.tsx` for other locales.
- Content: one MDX file per article per locale, e.g.
  `content/blog/en/how-to-draw-a-face.mdx`,
  `content/blog/es/como-dibujar-una-cara.mdx`. Frontmatter holds a shared
  `translationKey` that links the language versions, plus title,
  description, author, published/updated dates (real dates only).
- Slugs: localized Latin-script slugs for es/fr. For ja and ko prefer
  romanized or English slugs: native-script slugs become long percent-encoded
  URLs that are hard to share and copy.
- Each article only lists the locales it actually exists in
  (`availableLocales`), so hreflang never points to a missing translation.
- Articles are appended to the sitemap with the same `toEntries()` logic, with
  `localizedPaths` taken from the `translationKey` group.

## Browser-language detection (later, optional)

Automatic language redirects are **not** implemented, on purpose. If they are
added later, follow these rules:

1. **Never redirect on the server based on `Accept-Language` or IP.** Googlebot
   crawls mostly from the US without `Accept-Language`, so redirects can hide
   localized pages from search, and they break shared links.
2. Preferred approach: **a dismissible suggestion banner**, rendered on the
   client. It reads `navigator.languages` and suggests the matching live
   locale ("Ver esta página en español"). Search engines see each URL's own
   content unchanged.
3. The banner link points to the **equivalent page** (same `localizedPaths`
   entry), not the homepage, and **copies the full query string**
   (`window.location.search`) so `utm_*`, `gclid`, `fbclid` and `ttclid`
   survive.
4. Remember an explicit choice in a first-party cookie or `localStorage`
   (`preferred_locale`) and stop suggesting once dismissed. A cookie is only
   set after the user acts, never on the first response.
5. Exclude bots and in-app browsers where needed (`lib/in-app-browser.ts`
   already detects Instagram/TikTok/Facebook webviews).
6. If a server-side redirect is ever required anyway, it must: only apply to
   `/` (never deep links), use a `302`/`307` (not `301`), preserve the full
   query string, skip known crawlers, send `Vary: Accept-Language`, and keep
   `x-default` pointing to the English root.
